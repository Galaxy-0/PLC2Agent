# ADR-0001：采用 Agent-native IR 作为事实来源

- 状态：长期方向已接受，通用实现延后
- 日期：2026-07-16

## 背景

早期实验使用 OpenPLC Editor、OpenPLC Runtime、Factory I/O、CrossOver 和 Docker。虽然最终建立了 Modbus TCP 闭环，但出现了编辑器内存状态覆盖磁盘、变量声明丢失、周期配置被还原、上传成功却加载旧程序等问题。

这些问题说明：以人类 GUI 为中心的工程系统无法为 Agent 提供稳定、可审计的设计与验证接口。

## 决策

PLC2Agent 使用文本化、版本化、可校验的 PLC IR 作为唯一工程事实来源。厂商工程、ST、LD、I/O 表、HMI、模拟器配置和报告均由 IR 生成或通过 Adapter 同步。

## 当前执行状态

该决策描述长期架构，不要求当前实验阶段先实现通用 Schema、编译器或同步系统。

当前主线优先复用现有 ST 编译器、Runtime 和模拟器，通过可审查的 ST、I/O 契约、
测试和 Trace 跑通 Agent 闭环。只有当多 Runtime 或多 Plant Adapter 的实测差异证明
需要稳定的公共语义层时，才从已经验证的最小字段中提炼 IR。

因此：

- `specs/` 当前是目标样例和契约草案；
- `labs/` 中每个实验的 ST、I/O 映射和测试是该实验的实际事实来源；
- 不允许为了满足预设架构而提前开发通用框架；
- 未来 IR 必须从真实 Adapter 和闭环证据中生长，而不是凭空设计。

## 结果

正面影响：

- Agent 操作具备确定语义；
- 工程可 diff、review、test 和 migrate；
- Runtime 和可视化后端可替换；
- 需求到验证证据可以追踪。

代价：

- 需要自行定义 schema、编译降低和同步策略；
- 无法一开始覆盖所有厂商特性；
- 人类 GUI 编辑必须处理双向同步或明确设为只读投影。
