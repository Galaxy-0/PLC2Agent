# Agent-native PLC 工程系统

## 1. 产品定义

PLC2Agent 不是传统 PLC IDE 的自动点击机器人，也不是单一厂商工程格式的生成器。它是一个面向 Agent 的、可编译、可执行、可验证的自动化工程中间层。

传统工具的基本假设是：

> 人类操作 GUI，拖放梯形图、配置设备树、填写地址并在线监控。

PLC2Agent 的基本假设是：

> Agent 通过结构化接口理解需求、生成控制模型、编译部署、驱动数字孪生、分析时序轨迹并依据验证结果迭代。

## 2. 设计原则

### 2.1 IR 是事实来源

GUI、LD、ST、I/O 表、设备配置和报告都不能成为互相冲突的独立事实来源。统一 PLC IR 保存工程语义，其他形式均由它生成或同步。

这是长期架构原则，不代表当前阶段先实现通用 IR。现阶段先让每个 Lab 使用明确的
ST、I/O 契约、测试和 Trace 跑通闭环；待多个 Runtime 和 Plant Adapter 暴露出稳定
公共语义后，再提炼最小 IR。

### 2.2 行为契约优先于代码

能编译不代表控制正确。工程必须同时描述：

- 工艺需求；
- 信号与物理含义；
- 状态、动作和转换；
- 时序约束；
- 安全不变量；
- 故障模型；
- 恢复条件；
- 验收场景。

PLC 代码只是行为契约的一种实现。

### 2.3 Headless 优先

编译、部署、运行、读写变量、故障注入和验证必须具备无 GUI 接口。Web UI 用于人类理解和干预，但不阻塞自动化链路。

### 2.4 确定性与可重放

相同工程、种子、初始状态和输入序列必须产生相同轨迹。每次失败都应可重放到具体 tick，并显示相关输入、输出、状态和属性。

### 2.5 厂商后端可替换

第一版使用 OpenPLC，但上层工程不绑定 OpenPLC。CODESYS、Siemens、汇川、三菱和 Factory I/O 均以 Adapter 接入。

### 2.6 安全操作分级

读取工程、离线编译和仿真可自动执行；强制变量、部署真实设备、启动危险输出等操作必须经过策略检查，并支持人工确认。

## 3. Agent 闭环

```text
理解需求
→ 识别歧义和缺失信号
→ 建立 I/O、状态机、不变量和故障模型
→ 静态校验
→ 生成 PLC 程序及通信配置
→ 编译部署
→ 运行正常与异常场景
→ 分析轨迹和属性违例
→ 修改设计
→ 重跑验证
→ 输出可审计验收证据
```

Agent 的成功标准不是“成功点击上传”，而是给出需求到行为证据的完整可追溯链。

## 4. Factory I/O 的位置

Factory I/O 的本质是被控对象模拟器和三维可视化。它可以作为外部 Adapter 保留，但不是地基。PLC2Agent 自带的 Plant Simulator 优先保证：

- 脚本化模型；
- 批量运行；
- 故障注入；
- 状态快照；
- 时间旅行与回放；
- 自动判定；
- Git 可审查的文本格式。

二维或三维画面只是同一状态模型的投影。

外部仿真能力不限定于 Factory I/O。后期可以接入机器人、三维物理或专业工艺
模拟器，但它们必须通过 Plant Adapter 提供 PLC I/O、时间、状态和 Trace，不能把
PLC2Agent 变成通用物理仿真平台。复杂度分级和接入边界见
[仿真复杂度、阶段目标与边界](../architecture/simulation-scope.md)。

## 5. 首个纵向用例

首个用例是箱体自动分拣站：

- 启动、停止、复位和急停；
- 入口、类型、推料位和出口传感器；
- 主线、侧线和推料气缸；
- 自动、手动、停止和故障模式；
- 运输超时、出口堵塞、传感器卡死和气缸不到位；
- A/B/总产量；
- 自动 FAT 与时序报告。

该用例足以验证需求、I/O、顺控、安全、通信、仿真和验收的完整闭环，同时控制第一版复杂度。

## 6. 非目标

第一阶段不做：

- 通用三维 CAD/物理引擎；
- 完整替代 TIA Portal 或 CODESYS；
- 覆盖全部 IEC 61131-3 语言；
- 直接控制未经审查的真实危险设备；
- 以截图和 GUI 自动化作为核心协议；
- 一开始支持大量 PLC 品牌。
- 自研通用机器人动力学、流体、热力、电磁或 CNC 物理求解器；
- 接入与 PLC 控制、诊断或验收无关的通用模拟内容。

## 7. 长期方向

长期目标是形成 PLC 工程的 Agent OS：统一描述、生成、转换、验证和追踪跨厂商控制工程，并允许 Agent 在安全边界内进行设计空间搜索、自动调试、故障覆盖分析与变更影响评估。
